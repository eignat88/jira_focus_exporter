# 1. Назначение документа

Документ определяет правила работы AI-агентов, участвующих в реализации проекта обнаружения аномалий в операциях сканирования кодов маркировки.

Агенты должны выполнять задачи полного цикла:

* анализировать текущее состояние проекта;
* находить необходимые модули и зависимости;
* проектировать изменения;
* реализовывать программный код;
* создавать и изменять SQL-скрипты;
* выполнять тестирование;
* анализировать результаты;
* устранять ошибки;
* обновлять документацию и статус проекта.

Главная задача агентов — последовательно довести проект от текущего состояния до работоспособного аналитического контура:


# 2. Контекст проекта

Проект предназначен для выявления подозрительных паттернов при сканировании кодов маркировки на складских операциях.

Основные типы контролируемых аномалий:

1. слишком быстрое сканирование;
2. последовательности ошибок;
3. рост количества конкурирующих кодов маркировки;
4. отсутствие активности сотрудника;
5. несоответствие SSCC;
6. повторное использование кода маркировки;
7. нетипичное поведение сотрудника;
8. аномальное поведение маршрута;
9. отклонения по товару или складской зоне;
10. несогласованность данных между связанными сущностями.

В качестве источника используется Microsoft SQL Server с данными AX 2012. Целевая аналитическая база — PostgreSQL 17.

Основные слои данных:

```text
raw_ax — исходные данные AX;
dds    — очищенные и согласованные данные;
mart   — аналитические витрины и результаты моделей.
```

# 5. Основной принцип реализации

## 5.1. Сначала анализ, затем изменение

Перед изменением кода агент должен установить:

* где находится текущая реализация;
* какие классы и функции используются;
* какие зависимости существуют;
* какие таблицы затрагиваются;
* какие конфигурационные параметры используются;
* имеются ли тесты;
* имеются ли альтернативные реализации;
* какой вариант загрузчика используется: V2 или V2T;
* не реализована ли функция ранее в одном из модулей P0–P15.

## 5.2. Запрет параллельных реализаций

В проекте уже существуют:

```text
loader/
loader_v2t/
core/
application.py
main.py
config.yaml
```

Агент не должен создавать третий загрузчик или отдельный независимый pipeline без доказанной необходимости.

Новая функция должна встраиваться в существующую архитектуру.

## 5.3. Минимальные изменения

Агент должен выбирать решение, которое:

* решает поставленную задачу;
* минимально изменяет существующий код;
* сохраняет текущие интерфейсы;
* не ломает режим `resume`;
* не нарушает обратную совместимость;
* не требует переписывания рабочего контура без объективной причины.


## 6.4. Агент SQL и базы данных

### Назначение

Реализует SQL-скрипты, структуру PostgreSQL, миграции и проверки данных.

### Обязанности

* анализировать структуру SQL Server;
* проектировать таблицы PostgreSQL;
* создавать миграции;
* создавать индексы;
* создавать ограничения;
* создавать SQL для DDS и Mart;
* оптимизировать запросы;
* анализировать планы выполнения;
* обеспечивать повторный безопасный запуск;
* создавать проверки целостности.

### Требования к SQL

Каждый SQL-скрипт должен:

* иметь назначение;
* иметь комментарий;
* указывать входные таблицы;
* указывать создаваемые или изменяемые объекты;
* быть идемпотентным, где это возможно;
* выполняться в транзакции, если операция допускает транзакцию;
* не содержать необоснованный `SELECT *`;
* не использовать `DROP` без проверки существования;
* не выполнять массовое удаление без явного условия;
* учитывать объём таблиц.

### Для больших таблиц

Для таблиц объёмом в десятки или сотни миллионов строк агент обязан:

* исключать полное сканирование без необходимости;
* использовать подходящие индексы;
* проверять `EXPLAIN`;
* избегать одного большого `DELETE`;
* применять пакетную обработку;
* учитывать размер WAL;
* учитывать свободное место на диске.

## 6.8. Агент машинного обучения

### Назначение

Реализует модели обнаружения аномалий и единый ML pipeline.

### Модели

Агент должен последовательно реализовать:

1. Isolation Forest;
2. Local Outlier Factor;
3. Autoencoder;
4. LSTM Autoencoder.

Isolation Forest уже присутствует в проекте и должен использоваться как базовая модель для сравнения.

### Обязательные этапы

```text
получение признаков;
валидация датасета;
обработка пропусков;
масштабирование;
разделение по времени;
обучение;
подбор параметров;
scoring;
определение порога;
оценка;
сохранение модели;
запись предсказаний;
формирование отчёта.
```

### Запрет утечки данных

Агент не должен случайным образом перемешивать временные данные, если будущие записи могут попасть в обучающую выборку относительно тестовой.

Для временных признаков необходимо использовать последовательное разделение:

```text
обучающий период → валидационный период → тестовый период.
```

### Требования к моделям

Каждая модель должна сохранять:

```text
model_id;
model_type;
model_version;
feature_version;
training_period;
parameters;
threshold;
metrics;
artifact_path;
created_at.
```

### Сравнение моделей

Агент должен сформировать сравнительную таблицу:

| Модель | Найдено аномалий | Пересечение с базовой моделью | Стабильность | Время обучения | Время scoring |
| ------ | ---------------: | ----------------------------: | -----------: | -------------: | ------------: |

Нельзя выбирать модель только по количеству найденных аномалий.
